### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в доме.
- Система поддерживает только модули управления отоплением, которые подключает специалист компании при выезде. В коде включение и выключение — это смена статуса устройства через API.

**Мониторинг температуры:**

- Пользователи могут смотреть текущую температуру в доме через веб-интерфейс.
- Система поддерживает учёт датчиков (создание, изменение, удаление) и получает температуру запросом к датчику в момент обращения пользователя. История показаний не хранится.

### 2. Анализ архитектуры монолитного приложения

Приложение написано на Go, данные хранятся в PostgreSQL в одной таблице датчиков. Обработка запросов, логика и работа с данными находятся в одном приложении, которое разворачивается целиком. Всё взаимодействие синхронное: на каждый запрос температуры сервер сам ходит по HTTP к датчику (`temperature-api`) и ждёт ответа. Пользователей, домов и авторизации нет, API открыт.

### 3. Определение доменов и границы контекстов

Домены описывают целевую систему. В текущем монолите есть только их зачатки: учёт датчиков без привязки к дому и владельцу и текущая температура без истории, а пользователей, домов, сценариев, видео и уведомлений пока нет.

**Допущения**

- Комплекты устройств покупаются разово, вне системы. Тарифы и оплата не входят в рамки MVP.
- Корень модели — дом. Посёлки отдельно не моделируются.
- Устройства подключаются по открытым стандартным протоколам (например, Matter, Zigbee). Платформа работает с типами устройств и их возможностями, а не с конкретными моделями партнёров.
- Аутентификация реализуется готовым решением (Keycloak) с входом через Яндекс и Google.

### **4. Проблемы монолитного решения**

- Нельзя масштабировать отдельные части: рост числа устройств требует масштабировать всё приложение.
- Синхронный опрос датчиков: если датчик отвечает медленно или недоступен, запрос пользователя зависает или падает, а нагрузка растёт вместе с числом устройств.
- Модель знает только датчики температуры: новый тип устройства означает изменение кода и выпуск всего приложения.
- Нет самостоятельного подключения: каждая установка требует выезда специалиста, это не масштабируется на посёлки.
- Нет пользователей, домов и прав доступа, поэтому модель SaaS с самообслуживанием невозможна, а открытый API — риск для безопасности.
- Любое обновление требует остановки всего приложения.

# Задание 4. Создание и документирование API

### 1. Тип API

REST — для запросов, где клиенту нужен ответ сразу: данные устройства, его состояние, отправка команды. События через Kafka — там, где ответ не нужен и одно событие читают несколько сервисов: показания датчиков, изменения состояния, уведомления.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
